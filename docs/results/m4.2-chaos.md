# M4.2 chaos experiments: every event counted by ID

The chaos experiments from the [build plan](../plan.md) (M4, issue 2: *aggregator kill, sink outage, disk full; each asserts produced = delivered + counted drops (sampled, throttled), with duplicates removed by event ID*), run in one pass against a fresh `make up` with `make chaos` ([`bench/m4_chaos.sh`](../../bench/m4_chaos.sh)). Also the question left open by [#51](https://github.com/Andrew-Hinson/spillway/pull/51): does an agent that crashes lose logs?

**Result: no event lost in five of the six scenarios: aggregator kill, Loki frozen, cold storage frozen, agent kill and its control. A full disk lost a few acknowledged events, 47 across the sinks in one run, and that one isn't a pass.** Along the way the experiments found that the agent had been losing a third of a busy container's logs with no fault at all. That's fixed here.

| Scenario | Fault | Team `chaos` (drops nothing): hot / cold | Team `chaosdrop`: cold, and produced = hot + sampled + throttled |
|---|---|---|---|
| Aggregator kill | SIGKILL vector-aggregator-0 | **360,000 / 360,000**, 0 missing (cold: 483 duplicates) | 360,000, 0 missing (7 duplicates). 223,895 + 90,000 + 46,105 = **360,000**. The counters miss 2,896 of the drops: the killed pod's last increments |
| Hot sink outage | Loki frozen 2 min | **360,000 / 360,000**, 0 missing, 0 duplicates | 360,000, 0 missing. 221,939 + 90,000 + 48,061 = **360,000**, the counters exactly |
| Cold sink outage | Silo frozen 2 min | **360,000 / 360,000**, 0 missing, 0 duplicates | 360,000, 0 missing. 221,890 + 90,000 + 48,110 = **360,000**, the counters exactly |
| Disk full | An aggregator's data dir out of space | **359,975 / 359,995: 25 and 5 missing** (duplicates 42 / 1,277) | **359,983: 17 missing** (1,408 duplicates). The counters miss 4,249 of the drops (five restarts) |
| Pod logs, no fault (control) | – | **180,000 / 180,000**, 0 missing, 0 duplicates | – |
| Agent kill | SIGKILL the agent on the generator's node | **180,000 / 180,000**, 0 missing, 0 duplicates | – |

*Missing* and *duplicates* are counted by event ID, for every event of each run, in Loki and in the cold bucket. For `chaosdrop`'s hot sink, *sampled* is exact by ID: all 90,000 debug events were produced and none reached hot. *Throttled* is the rest of what's not in hot. Where Vector's counters agree, the table says so.

## Setup

| | |
|---|---|
| Run | 2026-10-13 17:03–18:09 UTC, commit `8018207`, fresh `make up` |
| Host | The [M4.1](m4.1-benchmark.md) machine: Ryzen 7 7800X3D, 61 GiB, kind with 1 control plane and 2 workers |

Kafka scenarios: 1,000 events/s into `chaos.load` (6 partitions) for 6 minutes. Pod-log scenarios: 500 lines/s (≈750 KB/s) written to stdout in namespace `chaos-pods` for 6 minutes |
| Teams | [`deploy/chaos/pipelines.yaml`](../../deploy/chaos/pipelines.yaml). **`chaos`** drops nothing: dedupe, redaction, hot and cold, from `chaos.load` and `chaos-pods`. **`chaosdrop`** reads the same topic, samples out `debug` (every fourth event, by sequence number) and has a 600/s budget against 750/s after sampling, so it throttles about 150/s. Both route cold |
| Faults | No Kubernetes object is changed. Pods are force-deleted with no grace (SIGKILL), and Loki or Silo is frozen with `pkill -STOP` from its kind node and resumed with `-CONT`. Disk full: below |

## Method

- **Counting:** after each run, `bench/eventcheck.py` exports every line Loki holds for the team, source and run, in 2-second windows (Loki returns at most 5,000 lines per query). It reads every object of the team's prefix from a copy of the bucket, and checks each event's ID against its run and sequence number.
- **Drained:** a run is drained when the teams' consumer groups have no committed lag in Kafka (`kafka-consumer-groups.sh`) and both sink buffers are empty, plus 75 s for the last cold batch. Vector's own lag gauge can't be used: after a rebalance moves a partition away, the old owner keeps exporting its last value. After the aggregator kill, one read 20 for 15 minutes.
- **Duplicates in hot are undercounted:** Loki drops a line identical to one it holds (same stream, timestamp and content). A disk buffer's replay after a crash re-sends byte-identical lines, so it's invisible there. Events re-read from Kafka are processed again, get a new `spillway.sink_at`, and do show. Cold storage keeps every copy.

## Findings

### 1. The agent was losing a busy container's logs, with no fault at all (fixed)

The first pod-log run lost 38,547 of 90,000 events, in blocks of about 10,000 that didn't line up with the agent kill. The control, with no fault, lost **30,485 of 90,000** (34%), in 10,000-event blocks every 60 s: 1–10,490, 30,585–40,582 and 60,588–70,584.

- **Cause:** `kubernetes_logs` looks for new files every 60 s by default (`glob_minimum_cooldown_ms`). Kubelet rotates a container's log at 10 MiB, which takes about 14 s at 750 KB/s, renames it, and later gzips it. The source never reads the renamed file, so what it hadn't read by the rotation was lost until the next scan found the new `0.log`.
- **Fix:** the agent now scans every second ([`vector/agent/vector.yaml`](../../vector/agent/vector.yaml)). The same control then delivered **90,000 of 90,000**, and in the recorded run **180,000 of 180,000**.

This is very likely the loss #51 couldn't attribute: fixture logs missing from 20:13 to 20:32 while an agent crash-looped.

### 2. A killed agent loses nothing at this rate

With the fix, killing the agent on the generator's node two minutes into the run lost nothing: 180,000 of 180,000 in both sinks, no duplicates. The replacement agent resumed from its file checkpoints, and its disk buffer held what it had read.

**The limit is kubelet's rotation, not Vector.** A dead agent keeps the logs it hasn't read only as long as kubelet keeps the files. In a trial before the fix, the replacement agent took 62 s to start. A container logging 750 KB/s rotates about four times in that time.

### 3. A full disk crashes Vector and loses acknowledged events (not fixed)

The scenario puts vector-aggregator-0's data directory on a 3,300 MiB tmpfs mounted over its volume's directory on the node, with a filler file leaving 200 MiB free. Then it freezes Loki so the hot buffer grows.

A tmpfs smaller than the buffers isn't possible: Vector refuses to start when its disk buffers' total `max_size` (3 GiB on an aggregator) exceeds the mountpoint's capacity. That check is a good safeguard, but it counts capacity, not free space. So a full disk can happen only when something else fills it.

What happened, from aggregator-0's log (seen in a trial run; the recorded run had the same outcome):

1. A buffer write failed with `No space left on device (os error 28)`. Vector logged *"An error occurred that Vector couldn't handle"*, killed its sinks after the 60 s shutdown grace, and exited with code 0. Kubernetes recorded each exit as `Completed`, not as a crash.
2. On restart, it found the last record of both buffers' data files unreadable (*"Last written record was unable to be deserialized. Corruption likely"*) and truncated each file to the last complete record.
3. With the disk still full, it crashed again: five restarts in the recorded run.

The truncated records were events whose Kafka offsets had already been committed, so they were never read again. The recorded run lost **25 (hot) and 5 (cold) of team `chaos`'s events, and 17 of `chaosdrop`'s in cold**: adjacent blocks around sequence number 63,000, a different block per buffer. A trial lost 14 and 41 the same way.

**Mitigation in Spillway:** each aggregator's buffers live on their own volume (4 GiB for 3 GiB of buffers), so only Vector writes there and its startup check covers it. A full disk would take another writer, or a volume shrunk under it. Making Vector treat a full disk as backpressure, and stop acknowledging records it might truncate, would be an upstream change. That's a candidate for the M4.5 Rust contribution.

### 4. Duplicates after a crash land in cold storage

After the aggregator kill, cold storage held 483 and 7 duplicates. Hot held none: replays from a disk buffer are identical lines, which Loki drops (see Method). The cold sink is at-least-once, like the rest of the pipeline. Dedupe is in memory per pod, so a restarted aggregator can't catch replays. Cold readers should deduplicate by `spillway.event_id`.

### 5. Drop counters undercount after a crash

`chaosdrop`'s drops are counted exactly when nothing restarts: in both outages, produced = hot + sampled + throttled with Vector's counters, to the event. After the aggregator kill they were 2,896 short, and after the disk-full crashes 4,249 short. A pod's counter increments since the last scrape (15 s) die with it. The events weren't lost: sampling is exact by ID (90,000 debug produced, 0 in hot), and hot plus the drops accounts for every event.

### 6. Other observations

- After the force delete, the replacement aggregator-0 restarted once with `Error` before running. It didn't happen again in an idle test, and its log was gone by the time I looked, so the cause is unknown.
- Before the agent fix, a pod-log run's own result lines could be rotated out of `kubectl logs`. The generator now also writes its run records to the container's termination message, which the script reads.

## How to reproduce

```bash
make up
make chaos                                  # every scenario, about 70 minutes
make chaos SCENARIOS="lokistop agentkill"   # or some of them; MINUTES, RATE, FAULT_AT, OUTAGE, FREE
```

The script builds the generator, creates `chaos.load` and both teams, runs each scenario, and prints the tables above. It never leaves a sink frozen or an aggregator on a tmpfs, even if it fails. Its files, including each run's generator log and the full results as JSON (every missing sequence number), go to `bin/chaos/<time>/`.
