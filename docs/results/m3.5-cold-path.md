# M3.5: cold path to object storage

2026-10-10 · local kind cluster from `make up` · Vector 0.58.0 · Silo RELEASE.2026-09-16 (a MinIO fork) · [ADR 0006](../adr/0006-silo-for-local-cold-storage.md)

Does a team routed cold get its complete redacted stream in object storage, partitioned by team and date and compressed, with no PII?

## Setup

`make up` now installs Silo (`make storage`) with a `spillway-cold` bucket and generated credentials, and the operator runs with `--cold-bucket`. Three cold-routed pipelines, applied together, were Ready through the canary in 2 m 11 s. Two of them, the `content` and `payments` examples, were `Invalid` until now.

| Team | Source | Policy | Routing |
|---|---|---|---|
| `content` | Wikimedia topic, ~37 events/s | budget 100/s | hot and cold |
| `payments` | pod logs from a generator: each second 4 debug and 2 info as JSON, 2 info as logfmt, 2 warn as klog | `debug: 0, info: 25`, budget 500/s | hot and cold |
| `fixtures-team` | the fixture injector's pod logs, 4/s | defaults | hot and cold |

`make fixtures RATE=4` ran throughout.

- **`content`** has no sampling and a budget above its load, so cold and hot match type for type. Its 22,669 cold events carry 22,669 distinct event IDs: no duplicates.
- **`payments`**' cold copy has every debug and info line, which sampling removed from the hot path: 2,880 = 4/s × 720 s for each.
- **`fixtures-team`**: 2,880 = 4/s × 720 s.

## Partitioned, compressed, no PII

`make cold-check` syncs the bucket and checks every object. The key must be `team=<team>/date=<YYYY-MM-DD>/…log.gz`, the object must be gzip, and every line must be a JSON event whose `spillway.team` and log date match the key. It also searches every line for fixture values:

| Team | Date | Objects | Events | Fixtures | Event bytes | Stored (gzip) | Ratio |
|---|---|---:|---:|---:|---:|---:|---:|
| `content` | 2026-10-10 | 62 | 57,584 | 7,688 | 78,710,331 | 11,052,480 | 14.0% |
| `fixtures-team` | 2026-10-10 | 61 | 7,546 | 7,546 | 4,007,937 | 342,872 | 8.6% |
| `payments` | 2026-10-10 | 59 | 18,490 | 0 | 5,175,146 | 111,159 | 2.1% |

**PASS: 83,620 events in 182 objects, 15,234 of them fixtures, 0 values leaked, no mismatched objects.** Gzip stores Wikimedia events at 14% of their size, and the repetitive generator lines at 2%.

The hot sink over the same period (`make leak-check WINDOW=12m`): 5,758 fixtures delivered, 0 values leaked.

An earlier run of this change used versitygw as the store, with the same results (52,879 events in 98 objects, 0 leaked; cold matching hot for `content`, and every `payments` line in cold). Swapping to Silo changed only the image, port, environment variable names and health probes.

The checker can fail: given a planted object with a phone fixture value, an event from another team, and a key outside `team=…/date=…/`, it reported the leak and both problems and exited 1.

## Found along the way: the agent ran out of memory

The first run of this test (with versitygw) found fixture pod logs stopping at 20:12. The agent on the injector's node had been OOM-killed into a crash loop. Since #49 sends pod logs through Kafka, librdkafka's default queue took the agent past its 256 MiB limit. #51 fixed it (capped queue, lz4, a 512 MiB limit), and this run is on that fix. Its PR has the memory measurements.

## Limitations

- **Batches of up to 60 s or 10 MiB:** the newest minute of cold data is still in the aggregators' buffers. The canary's bake (2 min) is at least twice that timeout, as the operator requires.
- **Partitioned by log time, not arrival time:** a late event lands in its own day's prefix.
- **The local store is single-drive Silo on one volume**, with no erasure coding. In the cloud the sink writes to S3 (M4.3).
