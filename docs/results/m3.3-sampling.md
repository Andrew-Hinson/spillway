# M3.3: sampling, dedup and per-team drops

2026-10-10 · local kind cluster from `make up` · Vector 0.58.0 · [ADR 0004](../adr/0004-parse-pod-logs-and-trust-only-the-stamp.md)

Three questions: does each team keep the share of each level its spec asks for, does dedup remove replayed events and nothing else, and can each team's drops be seen?

## Setup

Four LogPipelines, applied together, Ready through the canary in 2 m 13 s:

| Team | Source | Policy |
|---|---|---|
| `edits` | Wikimedia topic | the [example](../../examples/edits.yaml): `levelField: type`, `categorize: 0`, `log: 10`, budget 25/s |
| `wiki-all` | Wikimedia topic | none: the reference that `edits` is compared against (same topic, its own consumer group) |
| `checkout` | pod logs, `checkout` namespace | `keepPercent: {debug: 0, info: 25}` |
| `fixtures-team` | pod logs, `fixtures` namespace | defaults (redaction only) |

A generator in `checkout` wrote, each second, 4 debug and 2 info lines as JSON, 2 info lines as logfmt and 2 warning lines as klog. `make fixtures RATE=4` ran throughout.

## Dedupe drops replays, and only replays

300 recentchange-shaped events were produced twice each to the Wikimedia topic, keyed by `event_id` the way the feeder keys them, so each pair shared a partition.

| | `edits` | `wiki-all` |
|---|---:|---:|
| `<team>_dedupe` discarded | 300 | 300 |
| Distinct IDs in Loki | 50 | 300 |
| Copies of any ID in Loki | 1 | 1 |
| Copies in Loki that were the replay | 0 | 0 |

`edits` shows 50 because its 25/s budget cut the 600-event burst. On each aggregator, events in = events to the hot sink + dedupe drops, exactly (2,889 = 2,689 + 200 and 4,981 = 4,881 + 100 for `wiki-all`). Pod logs have no `event_id` and bypass dedupe: `checkout_ids` sent all 5,990 to `_unmatched`, so none were dropped as "duplicates".

## Drops are visible per team

Every metric of a team's components now carries a `team` tag, so the [dashboard](../../dashboards/pipeline.json)'s new Teams row shows each team's hot-sink rate and its policy drops by stage. One finding from reading the live metrics: a team's `<team>_src_pods` filter counts other namespaces' pod logs as intentional discards (`checkout_src_pods` "dropped" 138 in its first minute). The panel and `make sampling-check` sum only the `dedupe`, `sample` and `budget` stages for that reason.

The dashboard's "Errors + drops (1h)" stat used to add every discarded event. Over the hour of this run it would have shown 46,501, all of them intended drops by sampling, budget and dedupe. It now counts only unintended drops (`intentional!="true"`) and reads 0.

## Limitations

- **Dedupe is per pod and in memory.** It catches replays that reach the same aggregator. After a rebalance or restart, a replay lands on a pod whose cache is empty. M4's chaos runs still dedupe by event ID when counting.
- **Multi-line messages aren't joined.** Stack traces and config dumps arrive one line per event, and only the first line has a level.
- **A level in free text can mislead.** A text line containing ` level=debug` is sampled as debug.
