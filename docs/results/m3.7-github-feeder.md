# M3.7: second feeder, GitHub public events

2026-10-11 · local kind cluster from `make up` · Vector 0.58.0 · unauthenticated GitHub API

Does a second feeder with a different shape and rate flow alongside Wikimedia, and do Spillway's policies work on it?

## The feeder

`feeders/github` polls `https://api.github.com/events`. GitHub serves no stream: the endpoint returns the most recent events, newest first, in up to 3 pages of 100. Responses are cached for 5 minutes, and without a token the limit is 60 requests an hour. So the feeder:
- **Fetches pages until one contains an event it has already seen**, using the ETag on page 1, and remembers the last 10,000 IDs.
- **Spaces polls from the rate-limit headers**: at least `X-Poll-Interval` (60 s), and long enough that the same number of requests per cycle lasts until the window resets, keeping 3 requests in reserve. It honours `Retry-After` on a 403 or 429.
- **Keys and identifies each event by its GitHub event ID**, so an event served again after a restart reaches the same partition with the same `spillway.event_id`, and the pipeline's dedupe drops it.
- **Paces each cycle's events evenly over the wait before the next poll** (see below).

The `github.events` topic has 6 partitions, so budgets split evenly (ADR 0005). A token in an optional `github-feeder` Secret raises the limit. The tests here ran without one.

## Both feeds at once

Unclaimed feeder topics now share the platform path: `wikimedia` and `github` → `redact_feed` → `stamp` → `loki`. Over 12 minutes after `make up`:

| | Wikimedia | GitHub |
|---|---|---|
| Events/s in Loki | ~23 | ~1.9 (1,395 produced in 12 min) |
| Arrival | a continuous SSE stream | up to 300 per poll, polls minutes apart |
| Shape | flat recentchange events, ~1.5 KB | nested `actor`, `repo`, `payload`, ~0.7–2 KB, 15 event types |
| Types (12 min) | edit, categorize, log, new | PushEvent 424, PullRequestEvent 252, IssueCommentEvent 117, ReleaseEvent 95, IssuesEvent 80, … |

The feeder made 15 API requests in that time, all 200, with 50 left in the rate-limit window.

## Policies on GitHub events: the `oss` example

`examples/oss.yaml` reads `github.events` with `levelField: type`, `pushevent: 20`, a 4/s budget, hot and cold. For events logged 03:35–03:49, with cold storage (the complete redacted stream) as the reference:

| pushevent (keep 20%) | 767 | 158 | **20.6%** |
| pullrequestevent | 406 | 397 | 97.8% |
| issuecommentevent | 256 | 253 | 98.8% |
| issuesevent | 191 | 186 | 97.4% |
| releaseevent | 129 | 128 | 99.2% |

The 2,202 cold events carried 2,202 distinct IDs.

**Redaction on real PII:** GitHub events carry real people's details. Cold storage held 6,655 `oss` events with **0 email addresses** and 4,553 `[REDACTED]` masks. Loki's `oss` stream had 0 lines with an email. Strings like `pixi.js@8.22.0` and `tailwind-merge@3.7.0` (npm package specifiers in release notes) were correctly left alone: the email pattern needs a letter TLD.

## Two problems found, and fixed

**1. Bursts plus a budget filtered out whole event types.** Before pacing, each poll's 300 events reached the aggregators within a second. Each pod's throttle lets about 20 through per 10 s window, so it kept the start of each burst and dropped the rest. In GitHub's ordering, issue and PR events come earlier in a burst and push, create and delete events later. Over 03:12–03:24, before the fix:

| Type | Cold | Hot | Hot / cold |
|---|---:|---:|---:|
| pushevent (keep 20%) | 417 | **0** | 0.0% |
| createevent | 49 | **0** | 0.0% |
| deleteevent | 24 | **0** | 0.0% |
| pullrequestevent | 229 | 67 | 29.3% |
| issuecommentevent | 150 | 37 | 24.7% |

So the budget wasn't just thinning the feed: it removed whole event types, though the average rate (about 1.7/s) was under the 4/s budget. Now the feeder spreads each cycle's events evenly over 90% of the wait before its next poll, which turns the feed into a steady stream of 1–2 events/s. That gave the table above. An event now waits up to one poll interval (about 3 minutes) longer before it's produced, and GitHub's API caches for 5 minutes anyway.

**2. The canary rolled back a healthy pipeline.** The first `oss` rollout failed with "took in events for cold_s3 but delivered none in 2m0s". A new team's consumer group starts at the latest offset, so the canary got nothing until a poll's burst arrived in the last ~10 s of the bake. The cold sink batches for 60 s, so it hadn't uploaded yet. The operator now judges stalls only on events a sink had received by a checkpoint one batch timeout (plus 15 s) before the end of the bake. See the amendment to ADR 0002. After the fix, `oss` was promoted in 2m11s.

## Limitations

- **Unauthenticated, the feed is a sample:** about 300 events per poll, a few minutes apart, out of a firehose that's much larger. A token would allow polling every 60 s, but the 5-minute cache still bounds freshness.
- **Shutdown drops paced events not yet produced.** The API serves them again after a restart, and dedupe removes any repeats.
- **The pipeline dashboard was built for one feeder.** Its feeder panels sum over both feeders now.
